# API設計書：読書記録アプリ（本棚アプリ）

画面設計書（[screens.md](screens.md)）とDB設計書（[database.md](database.md)）をもとに、フロントエンド（Next.js）とバックエンド（Ruby on Rails）の間でやり取りするAPIを定める。

## 1. 概要

| 項目 | 内容 |
|---|---|
| 構成 | Rails はAPIモード（`rails new --api`）で構築し、画面は Next.js が担当する |
| 形式 | JSONでやり取りする（`Content-Type: application/json`） |
| URL | すべて `/api` から始める（例：`/api/shelves`） |
| キー名 | スネークケース（`cover_image_url` のように、DBの列名と同じ） |
| 日付 | `YYYY-MM-DD` の文字列（例：`"2026-09-26"`）。年月は `YYYY-MM` |
| 日時 | ISO 8601 形式（例：`"2026-09-26T10:00:00+09:00"`） |
| 認証 | なし（ローカル環境で1人が使う前提。要件定義書7章） |
| CORS | Next.js の開発サーバー（`http://localhost:3000`）からのアクセスを許可する |

- 「今日の日付」はサーバー側で決める（タイムゾーンは Asia/Tokyo）
- 並び順（position）は、列の中での 1 からの番号とする（database.md 5章）

## 2. エンドポイント一覧

| ID | メソッド | パス | 内容 | 主に使う画面 |
|---|---|---|---|---|
| API-01 | GET | `/api/shelves` | 本棚の一覧を取得する | SCR-01（本棚タブ）、MDL-01（本棚の選択） |
| API-02 | POST | `/api/shelves` | 本棚を作成する | MDL-02（作成モード） |
| API-03 | PATCH | `/api/shelves/:id` | 本棚名を変更する | MDL-02（設定モード） |
| API-04 | DELETE | `/api/shelves/:id` | 本棚を削除する | DLG-01 |
| API-05 | GET | `/api/shelves/:shelf_id/books` | ボード（3列の書籍）を取得する。検索・絞り込みもここで行う | SCR-01（ボード） |
| API-06 | POST | `/api/shelves/:shelf_id/books` | 書籍を登録する | MDL-01（登録モード） |
| API-07 | GET | `/api/books/:id` | 書籍の詳細を取得する | MDL-01（編集モード） |
| API-08 | PATCH | `/api/books/:id` | 書籍を更新する（本棚の移動を含む） | MDL-01（編集モード） |
| API-09 | PATCH | `/api/books/:id/move` | 書籍の列・並び順を変更する | SCR-01（ドラッグ&ドロップ） |
| API-10 | DELETE | `/api/books/:id` | 書籍を削除する | DLG-01 |
| API-11 | GET | `/api/tags` | タグの一覧を取得する（候補表示にも使う） | SCR-01（タグの選択）、MDL-01（タグ入力） |
| API-12 | GET | `/api/stats/monthly_reads` | 月別の読了冊数を取得する | SCR-01（ヘッダーの集計、12ヶ月グラフ） |

Rails のルーティングのイメージ：

```ruby
namespace :api do
  resources :shelves, only: %i[index create update destroy] do
    resources :books, only: %i[index create]
  end
  resources :books, only: %i[show update destroy] do
    patch :move, on: :member
  end
  resources :tags, only: %i[index]
  get "stats/monthly_reads", to: "stats#monthly_reads"
end
```

## 3. 共通の決まり

### 3.1 HTTPステータスコード

| コード | 使う場面 |
|---|---|
| 200 OK | 取得・更新に成功した |
| 201 Created | 作成に成功した |
| 204 No Content | 削除に成功した（本文なし） |
| 400 Bad Request | パラメータの形式が正しくない（例：`month=2026-13`） |
| 404 Not Found | 指定したIDの本棚・書籍がない |
| 409 Conflict | 今のデータの状態では実行できない（例：書籍が残っている本棚の削除） |
| 422 Unprocessable Entity | 入力チェックでエラーになった（例：タイトルが未入力） |
| 500 Internal Server Error | サーバー内部のエラー |

### 3.2 エラーの形式

エラーのときは、次の形式でJSONを返す。`message` は画面にそのまま表示できる日本語にする。

```json
{
  "error": {
    "code": "validation_failed",
    "message": "入力内容に誤りがあります",
    "details": {
      "title": ["タイトルを入力してください"],
      "rating": ["評価は読了の書籍のみ入力できます"]
    }
  }
}
```

| code | HTTP | 内容 |
|---|---|---|
| `bad_request` | 400 | パラメータの形式が正しくない |
| `not_found` | 404 | 対象が見つからない |
| `shelf_not_empty` | 409 | 書籍が残っている本棚は削除できない |
| `last_shelf` | 409 | 最後の1つの本棚は削除できない |
| `validation_failed` | 422 | 入力チェックのエラー。`details` に項目ごとのメッセージを入れる |
| `internal_error` | 500 | サーバー内部のエラー |

- `details` は `validation_failed` のときだけ付ける。キーは項目名（列名）とする
- 画面では、`details` がある場合は該当する入力欄の下に、ない場合は画面右下に `message` を表示する（画面設計書8章）

### 3.3 レスポンスで使うデータの形

**本棚（Shelf）**

```json
{ "id": 1, "name": "仕事用", "books_count": 14 }
```

- `books_count`：本棚に入っている書籍の数。MDL-02で［本棚を削除］を押せるかどうかの判定に使う

**書籍カード（BookCard）**：ボードのカードに必要な項目だけを持つ

```json
{
  "id": 7,
  "title": "リーダブルコード",
  "cover_image_url": "https://example.com/covers/7.jpg",
  "status": "done",
  "position": 1,
  "tags": [{ "id": 1, "name": "技術書" }]
}
```

**書籍（Book）**：編集モーダルに必要なすべての項目を持つ

```json
{
  "id": 7,
  "shelf_id": 1,
  "title": "リーダブルコード",
  "author": "Dustin Boswell, Trevor Foucher",
  "cover_image_url": "https://example.com/covers/7.jpg",
  "status": "done",
  "position": 1,
  "started_on": "2026-08-28",
  "finished_on": "2026-09-05",
  "rating": 5,
  "memo": "命名の章は何度でも読み返したい。",
  "tags": [{ "id": 1, "name": "技術書" }],
  "created_at": "2026-08-28T21:00:00+09:00",
  "updated_at": "2026-09-05T22:10:00+09:00"
}
```

- 値がない項目は `null` を返す（`author`、`cover_image_url`、`started_on`、`finished_on`、`rating`、`memo`）
- `tags` は付けた順に並べる。1つもない場合は空の配列 `[]` を返す

**タグ（Tag）**

```json
{ "id": 1, "name": "技術書" }
```

## 4. 本棚のAPI

### API-01 本棚の一覧を取得する

`GET /api/shelves`

- 作成順（`id` の昇順）で返す。本棚タブの並びに使う

レスポンス（200）

```json
{
  "shelves": [
    { "id": 1, "name": "仕事用", "books_count": 14 },
    { "id": 2, "name": "趣味用", "books_count": 10 }
  ]
}
```

### API-02 本棚を作成する

`POST /api/shelves`

リクエスト

```json
{ "shelf": { "name": "漫画" } }
```

レスポンス（201）：作成した本棚

```json
{ "shelf": { "id": 3, "name": "漫画", "books_count": 0 } }
```

| エラー | 条件 |
|---|---|
| 422 `validation_failed` | 本棚名が未入力、または50文字を超える |

### API-03 本棚名を変更する

`PATCH /api/shelves/:id`

リクエスト

```json
{ "shelf": { "name": "技術書" } }
```

レスポンス（200）：変更後の本棚（形は API-02 と同じ）

| エラー | 条件 |
|---|---|
| 404 `not_found` | 本棚がない |
| 422 `validation_failed` | 本棚名が未入力、または50文字を超える |

### API-04 本棚を削除する

`DELETE /api/shelves/:id`

レスポンス（204）：本文なし

| エラー | 条件 |
|---|---|
| 404 `not_found` | 本棚がない |
| 409 `shelf_not_empty` | 書籍が1冊以上残っている（要件定義書5.6） |
| 409 `last_shelf` | 最後の1つの本棚である（要件定義書5.6） |

- 画面では削除できない場合はボタンを押せなくしているが（画面設計書6章）、APIでも同じ条件を確認する

## 5. 書籍のAPI

### API-05 ボード（3列の書籍）を取得する

`GET /api/shelves/:shelf_id/books`

| クエリパラメータ | 必須 | 内容 |
|---|---|---|
| `q` | － | キーワード。タイトルまたは著者名に部分一致する書籍に絞り込む（英字の大文字・小文字は区別しない。要件定義書5.8） |
| `tag_id` | － | タグのID。そのタグが付いた書籍に絞り込む |

- 両方を指定した場合は、両方の条件に合う書籍を返す（AND条件）
- 各列の書籍は `position` の順に並べる

レスポンス（200）

```json
{
  "shelf_id": 1,
  "filtered": true,
  "columns": {
    "unread":  { "total": 4, "books": [ /* BookCard の配列 */ ] },
    "reading": { "total": 2, "books": [] },
    "done":    { "total": 8, "books": [ /* BookCard の配列 */ ] }
  }
}
```

- `filtered`：`q` または `tag_id` を指定したかどうか
- `total`：絞り込む前の、その列の冊数。絞り込み中は「表示中の冊数 / 全冊数」（例：`2 / 12`）の表示に使う（画面設計書4.2）。表示中の冊数は `books` の要素数を使う

| エラー | 条件 |
|---|---|
| 404 `not_found` | 本棚がない |
| 400 `bad_request` | `tag_id` が数値でない |

- 存在しない `tag_id` を指定した場合は、エラーにせず0件を返す

### API-06 書籍を登録する

`POST /api/shelves/:shelf_id/books`

リクエスト

```json
{
  "book": {
    "title": "三体",
    "author": "劉慈欣",
    "cover_image_url": null,
    "status": "unread",
    "started_on": null,
    "finished_on": null,
    "rating": null,
    "memo": "",
    "tag_names": ["小説", "SF"]
  }
}
```

- `title` 以外は省略できる。`status` を省略した場合は `unread`（未読）にする
- 登録した書籍は、指定したステータスの列の末尾に置く（要件定義書5.2）
- `tag_names` の扱いは 5.1 を参照

レスポンス（201）：登録した書籍（Book）

```json
{ "book": { "id": 31, "shelf_id": 2, "title": "三体", "...": "..." } }
```

| エラー | 条件 |
|---|---|
| 404 `not_found` | 本棚がない |
| 422 `validation_failed` | 入力チェックのエラー（database.md 9章、および 5.2 の整合性チェック） |

### API-07 書籍の詳細を取得する

`GET /api/books/:id`

レスポンス（200）：書籍（Book）

```json
{ "book": { "id": 7, "shelf_id": 1, "title": "リーダブルコード", "...": "..." } }
```

| エラー | 条件 |
|---|---|
| 404 `not_found` | 書籍がない |

### API-08 書籍を更新する

`PATCH /api/books/:id`

編集モーダルの［保存］で、フォームの内容をまとめて送る。

リクエスト

```json
{
  "book": {
    "shelf_id": 1,
    "title": "リーダブルコード",
    "author": "Dustin Boswell, Trevor Foucher",
    "cover_image_url": "https://example.com/covers/7.jpg",
    "status": "done",
    "started_on": "2026-08-28",
    "finished_on": "2026-09-05",
    "rating": 5,
    "memo": "命名の章は何度でも読み返したい。",
    "tag_names": ["技術書", "設計"]
  }
}
```

- 送った項目だけを更新する。`tag_names` を送った場合は、タグをその内容に置き換える
- 日付・評価は送った値をそのまま保存する。ステータスを変えたときの日付・評価の自動変更（要件定義書5.3）は、フロントエンドのフォーム上で行ってから送る（画面設計書5.3。利用者が保存前に日付を直せるようにするため）
- `shelf_id` または `status` が変わった場合は、移動先の列の末尾に置き、移動元の列を詰める（要件定義書5.6、database.md 5章）

レスポンス（200）：更新後の書籍（Book）

| エラー | 条件 |
|---|---|
| 404 `not_found` | 書籍がない |
| 422 `validation_failed` | 入力チェックのエラー。移動先の本棚（`shelf_id`）が存在しない場合も含む |

### API-09 書籍の列・並び順を変更する

`PATCH /api/books/:id/move`

ドラッグ&ドロップでカードを置いたときに呼ぶ。

リクエスト

```json
{ "status": "reading", "position": 1 }
```

| 項目 | 必須 | 内容 |
|---|---|---|
| `status` | ○ | 移動先の列（`unread` / `reading` / `done`） |
| `position` | － | 移動先の列で何番目に置くか（1から）。絞り込みを考えない、列全体での番号とする。省略した場合、または列の冊数より大きい場合は末尾に置く |

- サーバーは次の処理を1つのトランザクションで行う
  1. ステータスが変わる場合、日付・評価を要件定義書5.3のルールで更新する（database.md 6章）
  2. 移動先の列の `position` の位置に入れ、移動元と移動先の列の番号を振り直す（database.md 5章）
- 絞り込み中のドロップ（画面設計書4.4）
  - 別の列へのドロップ：`position` を省略して送り、末尾に置く
  - 同じ列の中へのドロップ：何もしないため、APIを呼ばない

レスポンス（200）：移動後の書籍（Book）。日付・評価が自動で変わった結果も含む

| エラー | 条件 |
|---|---|
| 404 `not_found` | 書籍がない |
| 422 `validation_failed` | `status` がない、または値が正しくない。`position` が1未満 |

- 画面は、ドロップした時点でカードを移動して表示し、APIがエラーを返したら元の位置に戻す（画面設計書4.4）

### API-10 書籍を削除する

`DELETE /api/books/:id`

- 削除した書籍があった列の番号を詰める。タグ付け（book_tags）も一緒に消える（database.md 4.2）

レスポンス（204）：本文なし

| エラー | 条件 |
|---|---|
| 404 `not_found` | 書籍がない |

### 5.1 タグ名（tag_names）の扱い

API-06・API-08 の `tag_names` は、次のように処理する（database.md 3.3.1）。

1. 名前ごとに前後の空白を取り除き、空になったものは無視する
2. 正規化したキー（`normalized_name`）で既存のタグを探し、あればそれを使う。なければ新しいタグを作る（`name` は送られた表記のまま）
3. 同じタグを指す名前が複数ある場合（例：`["Ruby", "ruby"]`）は、1つにまとめる
4. 書籍のタグを、この結果に置き換える

- タグ名が30文字を超える場合は 422 `validation_failed`（`details` のキーは `tag_names`）
- モーダルを［キャンセル］で閉じた場合はAPIを呼ばないため、タグも作られない

### 5.2 書籍の入力チェック

database.md 9章の文字数上限に加えて、次の組み合わせをチェックする（database.md 4.1 のCHECK制約と同じ内容）。

| 条件 | エラーの項目 | メッセージ |
|---|---|---|
| `status` が `done` 以外なのに `finished_on` がある | `finished_on` | 完了日は読了の書籍のみ入力できます |
| `status` が `done` 以外なのに `rating` がある | `rating` | 評価は読了の書籍のみ入力できます |
| `status` が `unread` なのに `started_on` がある | `started_on` | 読書開始日は未読の書籍には入力できません |
| `rating` が1〜5の整数でない | `rating` | 評価は1〜5で入力してください |
| `cover_image_url` が `http://` または `https://` で始まらない | `cover_image_url` | 書影URLは http:// または https:// で始まるURLを入力してください |

## 6. タグのAPI

### API-11 タグの一覧を取得する

`GET /api/tags`

| クエリパラメータ | 必須 | 内容 |
|---|---|---|
| `q` | － | 入力中の文字。正規化してから、`normalized_name` に部分一致するタグに絞り込む（database.md 3.3.2） |

- `q` を省略した場合はすべてのタグを返す。ツールバーのタグのセレクトボックスに使う
- `q` を指定した場合は、編集モーダルのタグ入力の候補に使う。入力のたびに呼ぶと多すぎるため、300ms ほど入力が止まってから呼ぶ
- 名前の順（`normalized_name` の昇順）で返す

レスポンス（200）

```json
{
  "tags": [
    { "id": 4, "name": "ミステリー" },
    { "id": 9, "name": "ミステリー小説" }
  ]
}
```

## 7. 集計のAPI

### API-12 月別の読了冊数を取得する

`GET /api/stats/monthly_reads`

| クエリパラメータ | 必須 | 内容 |
|---|---|---|
| `from` | ○ | 開始の年月（`YYYY-MM`） |
| `to` | ○ | 終了の年月（`YYYY-MM`）。`from` と同じか、それより後 |

- 全本棚の合計で、`status` が `done` かつ `finished_on` がその月に入る書籍を数える（要件定義書5.4、database.md 7章）
- 読了が0冊の月も `0` として含め、古い月から順に返す

使い方

| 画面の表示 | 呼び方 |
|---|---|
| ヘッダーの「読了 ○冊」（指定月） | `from` と `to` に同じ月を指定する（例：`?from=2026-09&to=2026-09`） |
| 12ヶ月グラフ | 今月を含む直近12ヶ月を指定する（例：`?from=2025-10&to=2026-09`） |

レスポンス（200）

```json
{
  "months": [
    { "month": "2025-10", "count": 1 },
    { "month": "2025-11", "count": 2 },
    { "month": "2026-09", "count": 3 }
  ]
}
```

（例では途中の月を省略している）

| エラー | 条件 |
|---|---|
| 400 `bad_request` | `from` / `to` がない、形式が正しくない、`from` が `to` より後、または期間が24ヶ月を超える |

## 8. 画面の操作とAPIの対応

| 画面の操作 | 呼ぶAPI | その後の画面の更新 |
|---|---|---|
| ボード画面を開く | API-01、API-05、API-11、API-12（指定月・12ヶ月） | 本棚タブ・ボード・タグ・集計を表示する |
| 本棚タブを切り替える | API-05 | ボードを表示し直す（絞り込み条件は維持する） |
| キーワードを入力する／タグを選ぶ | API-05（`q`・`tag_id` 付き。キーワードは300ms待ってから） | ボードを表示し直す |
| ［<］［>］で月を切り替える | API-12（指定月） | 「読了 ○冊」を更新する |
| カードをドラッグ&ドロップする | API-09 | 成功したら返ってきた書籍の内容でカードを更新し、ステータスが変わった場合はAPI-12で集計も取り直す。失敗したら元に戻す |
| ［＋書籍を追加］→［保存］ | API-06 | API-05、API-01（冊数）、API-11（新しいタグ）を取り直す |
| カードをクリック | API-07 | 編集モーダルに表示する |
| タグ入力欄に入力する | API-11（`q` 付き。300ms待ってから） | 候補を表示する |
| 編集モーダルで［保存］ | API-08 | API-05、API-01（冊数）、API-11、API-12 を取り直す |
| 書籍を削除する | API-10 | API-05、API-01（冊数）、API-12 を取り直す |
| 本棚を作成する | API-02 | API-01 を取り直し、作成した本棚に切り替える |
| 本棚名を変更する | API-03 | API-01 を取り直す |
| 本棚を削除する | API-04 | API-01 を取り直し、最初の本棚に切り替える |

## 9. 設計上の判断とその理由

| 論点 | 採用した設計 | 検討した他の案 | 採用理由 |
|---|---|---|---|
| Railsの構成 | APIモードでJSONだけを返す | フルスタック（画面もRailsで作る） | 画面は Next.js で作ると決めているため（要件定義書9章）。APIモードにすると、画面用の不要な機能が入らず構成が小さくなる |
| APIの形式 | REST（リソースごとのURL＋HTTPメソッド） | GraphQL | 画面が1ページでリソースも少なく、RESTで十分に表せる。Rails の標準の作り方にそのまま乗れる |
| 検索・絞り込みの処理場所 | サーバー（API-05 のクエリパラメータ） | 本棚の書籍を全件取得して、フロントエンドで絞り込む | 検索の条件（部分一致、大文字・小文字の区別、AND条件）をサーバー側で1か所にまとめられる。書籍が増えても、画面に送るデータ量が増えない。入力のたびに通信しすぎないよう、300ms待ってから送る |
| ボードの取得単位 | 本棚ごとに3列分をまとめて返す | 列ごと、または書籍一覧を1つの配列で返す | ボードは3列を同時に表示するため、1回の通信でそろうほうがよい。列ごとにまとめて返せば、フロントエンドで振り分ける処理がいらない |
| 絞り込み前の冊数 | API-05 のレスポンスに `total` として含める | 冊数を取得するAPIを別に作る | 絞り込み中の「2 / 12」の表示に必要で、ボードと同じタイミングで必要になるため |
| カードと詳細の分け方 | ボードはカード用の項目だけ返し、詳細は API-07 で取得する | ボードで全項目を返す | ボードに感想メモなどの長い文章まで含めると、表示に使わないデータが増える。編集モーダルを開くときに最新の内容を取得できる |
| ドラッグ&ドロップのAPI | 移動先の `status` と `position` だけを送り、振り直しと日付・評価の更新はサーバーで行う（API-09） | 移動後の列の並び（書籍IDの配列）を丸ごと送る | 絞り込み中は画面に見えていない書籍があり、フロントエンドでは列全体の正しい並びを作れない。日付・評価のルールもサーバーで1か所にまとめられる |
| 編集モーダルでのステータス変更 | 日付・評価の自動変更はフロントエンドのフォーム上で行い、API-08 は送られた値をそのまま保存する（整合性はチェックする） | API-08 でもサーバーが自動変更する | モーダルでは、ステータスを変えたあと日付を直してから保存できる（画面設計書5.3）。サーバーが上書きすると、利用者が直した日付が消えてしまう |
| タグの渡し方 | 書籍の登録・更新時にタグ名の配列（`tag_names`）で渡す | 先にタグを作成するAPIを呼び、書籍にはタグIDの配列を渡す | 1回の通信で保存が済む。表記ゆれの判定をサーバーの1か所にまとめられる。モーダルをキャンセルしたときに、使われないタグだけが作られることがない |
| タグの作成・削除API | 作らない（書籍の保存時に作成する） | タグを管理するAPIを用意する | 要件定義書5.7で、タグは書籍に付けるときに作成するとしている。タグの削除・名前変更はMVPの範囲外 |
| 集計のAPI | 期間（`from`〜`to`）を指定する1つのAPIで、指定月の冊数と12ヶ月グラフの両方に使う | 指定月用とグラフ用で別々のAPIを作る | どちらも「月ごとの読了冊数」で、期間が違うだけのため。0冊の月もサーバーで補うので、フロントエンドは受け取った配列をそのまま表示できる |
| キー名 | スネークケース | キャメルケース（`coverImageUrl`） | DBの列名・Railsの標準と同じにしたほうが、変換の処理がいらず、APIとDBの対応もわかりやすい。フロントエンドでは型定義（TypeScript）でスネークケースのまま扱う |
| エラーの形式 | `error.code` と日本語の `message`、項目ごとの `details` | HTTPステータスコードだけで判断する | 同じ409でも理由（書籍が残っている／最後の1つ）によって表示を変えるため、`code` で区別する。`details` があれば、入力欄ごとにエラーを表示できる（画面設計書8章） |
